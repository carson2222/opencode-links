# opencode-links

OpenCode V2 plugin for the TUI and OpenCode Desktop: per-chat Linear issues, PRs and local pages, for people who run many chats in parallel. Public repo `carson2222/opencode-links`, npm package `opencode-links`.

`LINEAR.md` records the approved Linear scope, configuration and limits.

## Product decisions

Carson, the maintainer, made these. Ask him before changing anything user-facing: layout, colors, copy, settings, which PRs or pages count.

- Scope is one chat (root session) and its subagents. Never show other chats' PRs or machine-wide servers.
- PRs (approved 2026-10-28) count when this chat or its subagents created, worked on or monitored them, or the user pasted their URL in a root message. Created: exit 0 and a non-help `gh pr create` whose URL is printed alone on a line, not in the command, and attributable to it: no other statement could reprint old output (file readers, interpreters, `gh … view|api`, unsafe echo), or, if one could, the create's own exit decides the command's (`&&` to the end, no pipe), its stdout reaches the output, it is not `--web`/`--dry-run`, the output holds exactly one PR URL (in the create's repo) and is not truncated, and no statement is a control builtin, function, group, override or background job. Linear PR-ownership IDs use the same proof. Worked on: the chat issued `gh pr merge|close|ready|reopen|edit|comment|review|checkout` on a specific PR as real command text (top level or inside `( … )`/`{ …; }`, not quotes, heredoc bodies, echo/printf args, comments, functions, conditionals or loops), whether or not it succeeded; `false &&` and `true ||` positions count. Monitored: issued `gh pr checks <ref>` or `gh pr view <ref> --json` with `statusCheckRollup|reviewDecision|mergeStateStatus|reviews|latestReviews|reviewRequests`, stdout shown to the agent; not lists, searches, loops or more than three in one command. Bare numbers need the invocation's repo (`-R`, `GH_REPO`, a URL, or the git remote of the directory it runs in; `~` and `$HOME` expand, unresolvable directories give no row). Mentions, plain views, pushes alone and branch names do not count.
- PR row: `#number repo Short title`. Status is shown by the number's color only, never as text: open, draft, merged, closed. GitHub colors by default; white means unknown. No CI, reviews or comments. Newest first.
- Local row: concrete loopback URLs (localhost, 127.x, [::1], *.localhost, any port) that the main agent wrote in its replies, plus dev-server banners (`Local:` lines, standalone portless `-> https://….localhost` lines) of servers the main agent started: output of a command that starts one (package `dev|start|preview|serve` scripts, vite, next, astro, portless run and similar, foreground or background) in an executed position (unconditional or in an `&&` chain from its list's start, never right of `||`; commands with `if`/`while`/`case`/functions are skipped), or a `read`/`cat`/`tail`/`sed`/`grep` of a log such a command redirected to or a background shell streamed to (per-root `logs` in `chats`; relative paths resolve against `workdir`, else the session directory). Any sibling that could print other text (echo/printf of URLs, interpreters, other files) voids the banner. A raw `Local:` origin behind a portless proxy in the same output is dropped for its public origin. Not subagents, `portless list`, transcripts (`opencode`, `sqlite3`) or prose. Deep paths are kept. A dead server dims the row and never hides it.
- Click opens the URL. Hover scrolls a cut-off title. An empty section is hidden. One muted hint line appears when `gh` is missing or signed out.
- Hover reveals `×` to hide a PR or local page in this chat only. Dismissals survive rescans and reopening; they never change the PR or stop the server. The command palette's `Restore hidden links` restores this chat's links.
- Linear rows show an ID colored by the real workflow and a short title. Requested issues first, then other associated issues newest first. Five rows initially, with expansion. Click, hover, hide and restore work like PRs; `Link issue to this chat` handles ambiguous input. The plugin never writes to Linear.
- Options (TUI: `cli.json`; Desktop: the plugin's `opencode.json` entry; same names): `colors` (`github` | `theme`), `refresh` (seconds, min 15; unset = adaptive, set = ceiling on the visible-row interval), `prs`, `pages`; `linear` is off by default, `true` for URL tracking or `{ "workspace": "slug", "teams": ["TEAM"] }` for bare IDs too.
- Never reference or credit other plugins or products in code, docs or package metadata.

## How it works

- UI-only; no server part. One framework-free core serves both apps through `src/host.ts` (`Host`: durable stores, memory, client, events, cached session lookup). `src/links.ts` composes the core and display rules; `src/watch.ts` is the per-chat catch-up/refresh/probe cadence and marks entries: one timer set to the earliest due row (capped at 10 s), not a fixed tick. `src/tracker.ts` owns the single checkpointed history pass and live events. `src/extension.ts` defines discovery callbacks; `src/provider.ts` is the view-first scheduler shared by PRs and Linear: per-resource policy, union batching, background piggyback, claims, backoff and dirty marks. `src/stats.ts` keeps local hourly counters; `src/viewed.ts` stores per-root entry times. `src/issues.ts` stores Linear associations/aliases; `src/linear.ts` detects and batch-loads via CLI. Pure detectors (`pulls.ts`, `pages.ts`, `linear.ts`, `github.ts`) have no host.
- Persisted shapes are Effect Schemas in `src/schema.ts`; types derive from them. The core imports them type-only, so the TUI never loads Effect.
- TUI: `tui.tsx` (shipped as `dist/tui.js`) renders rows and commands; `src/tui-host.ts` adapts `Plugin.Context` (Solid stores, so rows stay reactive).
- Desktop (`src/gui.tsx` → `dist/gui-experimental.cjs`): the Electron main process runs the only tracker for the app (`src/desktop/main.ts`, `host.ts`, `controller.ts`). It has Node, the login-shell PATH and synchronous storage; windows have none of that and their stores don't sync live. Windows talk to it over the `opencode-links.links` Ipc (`src/desktop/contract.ts`): `watch` reports the sessions a window shows (`active` = a visible surface), per-window `state` pushes display-ready views (`view.ts`), and `dismiss`, `restore`, `link` act on the root chat. Main resolves roots, runs the watch cadence per root while a visible surface watches it, and gates network on that window's `BrowserWindow` focus. Only the app's own server (sidecar) is tracked. `src/desktop/data.ts` is the window accessor. The only surface is header chips (`header.tsx`, `Slot` `session.header`); `glance.ts` ranks which chips earn a slot and fits them in a share of the title row's width, measured with a hidden copy. `+N`, `…` and the **Show links** command open the full list (`dialog.tsx` → `list.tsx`). Linear colors are contrast-adjusted against the element's measured background (`look.ts`).
- Desktop keeps its own stores (Desktop state DB, `plugin.opencode-links`). On first start it imports the TUI cache once, read-only and schema-validated, from `$XDG_STATE_HOME/opencode/<channel>/tui/` (`prod` → `latest`); after that the two apps never share writes.
- Live detection: `session.tool.input.started` (name `shell` or `read`) → `session.tool.called` → `session.tool.success`. Failed shell calls that launched a shell (`metadata.shellID` on the live `session.tool.failed` or the stored `error` part) still record and invalidate worked-on and monitored PRs, never created ones; declined, blocked or never-started calls count for nothing. Shell commands are parsed per statement (`src/shell.ts`, shared with Linear); `src/remote.ts` resolves bare PR numbers from the local git config (no network). Pages come from `session.text.ended` and tool output on the root session; PR URLs from root `session.inbox.enqueued`. Event handlers only persist; they never touch the network.
- Local URL parsing handles inline Markdown, not the full Markdown grammar. Fenced code, escaped delimiters and nested link labels are not parsed as Markdown structure.
- History keeps per-session marks and verified idle stamps. Separate PR (`pullsVersion`), page and Linear detector versions enable one-time backfills of only that detector; page backfills read only root assistant history. Root user messages have their own checkpoints and detector versions (`userCheckpoint` for Linear, `pullsUserCheckpoint` for PR links), so request-parser fixes never replay child tool history. History walks all descendants, not only direct children. Save successful chunks before advancing checkpoints; failed children retry independently. A failed live save marks its chat for a catch-up scan. Catch-up runs on mount/root change/reconnect and focused retries, not focus alone. Memoize the root ID so cache hydration cannot cancel unchanged-root work. Cached-row refresh starts alongside history, not after it. Blur/unmount aborts history and vendor reads; focus state survives plugin reloads.
- `gh` and `linear` run by name; on "not found" `src/cli.ts` loads the login shell's environment once (`-il`, then `-l`) and retries, because Desktop keeps launchd's bare PATH when its own launch-time shell probe times out.
- Network work runs only from a mounted section (Desktop: a visible surface) while the terminal (Desktop: that window) is focused; blur and unmount abort it. Every non-dismissed row of a watched chat refreshes, not only the rendered ones. Requests coalesce for 100 ms; a provider keeps the latest references per chat and loads the union in one batch per host/workspace (40 per batch); canceled or empty requests do not start reads. `gh` uses `--include` for status and rate-limit headers.
- View-first cadence, per resource: entry (mount, root change, focus, reconnect, another surface of the root opening) re-reads non-merged rows whose last read started over 15 s earlier; a reused younger snapshot gets one confirmation at its 15 s age while the chat stays foreground. While viewed: 60 s after a change until two unchanged reads a minute apart, then 120 s; closed PRs and done/canceled/duplicate issues 10 min; merged PRs never, except a day-old title on entry. Explicit `refresh` caps the active intervals. Background chats never start requests or probes: a foreground request fills spare room in its batches with eligible keys from the shared stores (dirty first; roots viewed <24 h or with a dirty row: mutable older than 5 min; viewed <7 days: older than 1 h; older roots wait for entry). TUI and Desktop are separate cache domains.
- While an entry read is pending, a non-merged status last verified over 10 min ago renders in the neutral/unknown color (TUI and Desktop `stale`).
- Only verified reads advance `checked`. Nonzero `gh` exits, GraphQL errors and unparsable output are failures; a PR absent from a valid response (`NOT_FOUND`) is a normal read. A PR that never resolved and is still absent on a read over 10 minutes after its detection is not shown (typos in `-R`); one that ever had a title keeps showing. Transient failures retry after about 5/15/30/60 s, rate limits at the reported reset; failures back off only their rows, even when a row fails alone; a whole-batch failure shows the hint without gating. Missing, signed-out and rate-limited CLIs gate the whole provider; workspace mismatches stay row-scoped.
- Dirty marks (`refresh.*` `dirty`) force re-reads newer than a row's last read start. Live `gh pr merge|close|ready|reopen|edit|comment|review` completions mark the chat's targeted PRs at receipt time; `merge` and `ready` add +15/30/60/120 s. Live Linear detections mark their issues at success time. An observed PR state change marks the chat's issues at +3 s and +15 s. Marks at or before receipt are invalidation generations (`dirty`); future ones are timed rechecks (`rechecks`). A completed read drops only generations at or before its start; a merged result also drops pending rechecks; closed and done rows keep theirs until they run, since they can reopen. Never drop newer generations. Claims and marks under a Linear identifier alias move to the UUID key when it resolves. Never infer a status from a command.
- Probes send HEAD to the origin, 4 at a time, with a 5 s timeout, without TLS verification (Bun `fetch` in the TUI, `node:https` in Electron main, whose `fetch` rejects local self-signed certs). Refused, 502–504, or a 404 with `x-portless` means down. The next probe is due 10 s after the previous one started. A timeout keeps the last state.
- Durable stores `chats`, `status`, `linear`, `hidden`, `refresh.github`, `refresh.linear`, `viewed`, `stats` sync across TUI windows. `stats` holds 7 days of hourly counts (requests counted when sent, failures, keys, piggybacked keys, batch sizes, entry status ages, entry revalidation latency); `bun run stats` prints the TUI copy (`$XDG_STATE_HOME/opencode/latest/tui/plugin.opencode-links.stats.json`). Desktop keeps its own copy in its state DB. Chat membership expires after 90 days without visits; dismissals persist separately. Every store write rewrites the whole value (`chats` is about 1 MB on a heavy Desktop; each write costs ~20 ms of main-thread work there), so a chat entry is written only when it changes or when its `touched` stamp is over an hour old. Linear identities use organization/issue UUIDs with old identifier aliases. Page repairs retain source-backed malformed URL aliases so corrected rows respect old dismissals. Never change existing PR/page hidden keys during migrations.

## Develop

- `bun install`, `bun test`, `bunx tsc --noEmit`, `bun run build`. The build writes the Desktop bundle (the Vite preset fails on modules the app doesn't share) and `dist/tui.js` (`scripts/build-tui.ts`): OpenTUI's Solid transform skips `node_modules`, so an npm install loads raw `tui.tsx` as React JSX and fails. Shared modules compile to the host's `opentui:runtime-module:` ids. Target: the official Bun-based OpenCode binary, `>=2.0.24`; Desktop needs 2.2.0's GUI plugin API.
- Carson's own setup runs the npm release, listed in `~/.config/opencode/cli.json` and `opencode.json` `plugins`. A `plugins` entry with a checkout's absolute path loads that checkout's `dist/` instead, so rebuild after each change.
- Prove packaging changes through a real npm install: `npm pack`, then a sandbox TUI (below) with `"plugins":["opencode-links@file:<tarball>"]`. A local path entry skips the npm loader.
- Desktop loads plugins from the global `opencode.json` `plugins` and reloads a local checkout on each rebuild of `dist/`. Listing it there also lists its TUI part to TUIs, but without options; the `cli.json` entry for the same package wins, so keep options in both.
- Test Desktop only in an isolated harness (`OPENCODE_DESKTOP_TEST_ROOT`), never Carson's app. `bun scripts/fixture.ts --root <session> --dir <XDG_STATE_HOME>/opencode/latest/tui` writes fake cache rows that Desktop's one-time import picks up. Unit tests cover main with fake storage, client and windows (`test/desktop.test.js`).
- Never test against live OpenCode state: its tabs, plugin storage and sessions are Carson's. Run the real TUI in a sandbox instead:
  - `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` pointed at a temp dir, `opencode --standalone`, and `OPENCODE_CLI_CONFIG_CONTENT='{"plugins":["<absolute repo path>"]}'`.
  - Real chats: run `opencode session export <id>` on the live service (read-only). Import with `XDG_CONFIG_HOME` also isolated plus `opencode service set port <free port>`. The import starts an isolated service; stop it with the same env.
  - Isolating `XDG_CONFIG_HOME` also signs `gh` out. That is how the signed-out hint is tested.
  - Live events without cost or real PRs: free model `opencode/big-pickle` via `OPENCODE_CONFIG_CONTENT`, `--auto`, and a prompt that runs `true || gh pr create; echo <existing PR URL>`.
  - To observe clicks and `gh` calls, put logging shims named `open` and `gh` first on `PATH`.
- See the rendered sidebar: `bun run screen --color --from 124 --cwd <dir> -- opencode --standalone -s <session>` prints the real screen with colors; `--html` saves an image-ready render, `--keys` sends input, including mouse and focus escape codes.
- On macOS, `bun run smoke` checks the actual plugin in an isolated real TUI with synthetic cached rows, a loopback server and fake CLI/browser openers. It covers exact opener counts, expansion, hide/restore and native hyperlink rendering. It does not test real Ghostty Cmd-click. Never let a test overwrite the system clipboard; set `terminal.copy: "manual"` in sandbox CLI settings.
- `bun run simulate` replays a synthetic 8-hour day (real plugin code, virtual clock, fake `gh`/`linear`) against another revision (`--old <rev>`, default `main`) and prints vendor calls/hour, status age at entry and time to verified status per resource and per entry (all shown statuses), for one TUI and for 2 TUIs + Desktop. Its numbers are synthetic.
- `bun run smoke:refresh` covers stale-cache mount/root switches, injected slow history, blur/refocus and newly discovered rows during a metadata load. Fresh-cache click checks alone do not verify refresh latency. Report synthetic vendor timings separately from live service measurements.
- Check dismissal in the real TUI: hover, hide, reopen, then Ctrl+P → `Restore hidden links` → Enter. The palette command's layer needs `mode: "global"` to remain available while the palette owns input.
- Linear gates also cover manual linking, five-row expansion, auth hints, exact URL clicks, alias/UUID dismissal, blur/refocus and a read-only real CLI metadata load. Never execute ticket mutations to test detection; replay real history or use fake CLI output.
- Before claiming a detection change works, rerun it against real history: read `~/.local/share/opencode/opencode.db` read-only (`?mode=ro`, table `session_message`) and compare detected PRs with `gh pr create` calls. For pages, check exact reply text against independently expected URLs; replaying the same detector alone does not establish coverage.

## Releases

- Every change lands on `main` through a PR; CI (`.github/workflows/ci.yml`) runs tsc, tests and the build. Carson reviews README copy changes.
- To release, bump `version` in `package.json` inside the PR (semver; fixes are patches). Merging it runs `.github/workflows/release.yml`: tests, `npm publish` through npm trusted publishing (no token; it is bound to that workflow file name), then the `v<version>` GitHub release. `prepack` builds `dist/`. OpenCode installs see the update within a day.
- Open risks:
  - Mixed plugin versions writing the same TUI store (hot reload) drop newer optional fields (`pullsVersion`, `pullsUserCheckpoint`, `rechecks`, `logs`), causing one extra backfill after the last old writer stops.
  - A first Linear backfill can be large in chats with hundreds of subagents; it is lazy, chunked and cancelable. Warm scans skip completed sessions. See `LINEAR.md`.
  - The shared row handler must stop handled click events before OpenCode's own hyperlink opener runs. Verify exactly one OS opener call in the real TUI; native Ghostty Cmd-click still needs a real-terminal check.
  - Remote-server and Node-based TUIs are untested.
  - Desktop: the GUI API is experimental. Sessions on other servers (SSH, WSL, remote) show no links.
